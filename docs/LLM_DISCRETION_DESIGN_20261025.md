## 0. 結論（6行）

1. **いまの帳簿Aは MT5 のシステムトレードと同型。** 決定 32 行すべて `target_weight=0.5`（2資産で合計 1.0）/ `regime_state=RISK_ON` / `halt_flag=false`。自由に動く余地が 1 つもなく、唯一の撤退条件 `close < SMA200` は 14 日間で一度も発火していない（距離 +10.06〜+19.63%）。
2. **LLM を挟む価値があるのは 2 か所だけで、しかも同じノブ。** ①グロス上限（reduce-only の裁量）②撤退の判断材料。銘柄選択・配分比率・執行・安全停止は機械で十分か、LLM を入れると危険（§2）。
3. **材料は全部無料で取れる。** 8 系統を実測（合計 0.8 秒・並列時、有料契約 0 件、API キー 0 件）。ただし「向き」はこの 14 日では判定できない（n=15、符号が混在。§3-3）。
4. **コストは 1 回 ¥0.033〜0.138（実測の提供元 list 単価 × USDJPY 156.8）、遅延は 2.6〜13.3 秒。** 約定価格は 01:00 UTC の固定足始値なので、**締切（00:50 UTC）に間に合えば遅延の執行価格への影響はゼロ**（余裕 29.5 分。§6）。
5. **試作は既存 journal に影の帳簿 D を 1 つ足すだけ。** 新サービス・新 cron・新監視は作らない。判定は 20 営業日、A との DD比と累積（§7）。
6. **注意: LLM は「儲ける装置」ではない。** この 14 日の損益の 3 日分（最悪3日 -8.5pp / 最良3日 +7.0pp）が勝負のほぼ全部で、当てられなければ縮小は上昇日の取り分を削るだけ（§2-3 の数値）。だから設計は「下振れだけを削る非対称」に寄せる。

## 2. 判断点の棚卸しと切り分け（受入 (1)）

### 2-1. 7つの判断点

| # | 判断点 | いまの決め手（コード位置） | 機械ルールで十分か | LLM の総合判断が効くか | 判定 |
|---|---|---|---|---|---|
| P1 | 銘柄選択（BTC/ETH の 2 本） | universe 固定（`paperloop.py:1665`） | 十分（n=2、選定基準なし） | 効かない（材料がない） | **機械** |
| P2 | グロス（合計エクスポージャ） | `weight = 1/len(active)`（`backtest.py:432`）＝常に 1.0 | **不十分**（SMA200 が RISK_ON の間は無条件 100%） | **効く**（DD深・混雑・見出しリスクを統合） | **LLM** |
| P3 | 決定タイミング（日次 00:20 UTC） | `ops/demo-loop/daily.sh` の cron | 十分（日次で足りる） | 部分的（指標発表の前後を避ける） | 機械＋材料 |
| P4 | 撤退（リスクオフ） | `close < SMA200` の 1 条件だけ | **不十分**（14日で発火 0、距離 +10〜+20%） | **効く**（撤退の材料を増やす） | **LLM** |
| P5 | 資産配分（50/50 等金額） | `1/len(active)` | 十分（逆ボラにしても実測 +0.09pp、誤差） | 効かない | **機械** |
| P6 | 執行（1h足始値・15bps） | `apply_fill` / `paper_fill_bar_open_ts` | 十分（観測コストは仮定の 0.283 倍と良好） | **入れてはいけない**（遅延とスリッページだけ増える） | **機械** |
| P7 | 安全停止（データ失効・非有限値・5σ・cusum・guard） | `_halt_triggers_asset` / `evaluate_halt` / `paperloop_guard.check_trade` | 十分（かつ LLM より信頼できる） | **入れてはいけない**（判断を誤ると止まらない） | **機械のみ** |

**結論: LLM に渡すのは P2 と P4 だけ。しかも両者は同じノブ（グロスを下げる権限）に統合できる。** 他の 5 つは機械のまま。これが「ルールは補助、LLM が主役」を最小の変更で実装する形になる。

### 2-2. 渡す形（主役と補助の関係）

- LLM の出力は **目標グロス 1 個（0〜機械側の値）**。銘柄間の配分は機械が決めた比率のまま按分する（LLM は配分を触らない）。
- 機械側は「LLM が言った値」と「機械の値」の **小さい方**を実行する。LLM は機械の上限を超えられない（レバレッジ禁止は既存の `assert sum(target) <= 1` と同じ思想）。
- したがって LLM が壊れても、最大の被害は「機械と同じ」に戻ることだけ。**LLM の失敗は損ではなく、裁量の消滅**として扱う。

### 2-3. この 14 日で「当てる」ことの値段（実測の算術）

帳簿A の `mtm` 行 18 本（10-10 に再実行由来の重複 3 本）から作った 17 本の連鎖リターン（実質 15 日ぶん、10-11〜10-25）を使った感度（`arith.py`）。再確認として、グロス 1.0 の行が実測の -4.313% / -5.087% に一致する。

| ケース | 累積 | 最大DD | DD比（対 1/N ベンチ） |
|---|---|---|---|
| 現状（グロス 1.0・固定） | -4.313% | -5.087% | 0.9717 |
| 常時 0.75 に縮小（LLM が毎日 0.75 と言った場合） | -3.219% | -3.809% | 0.7274 |
| 常時 0.62（DD比 0.60 になる水準） | -2.651% | -3.141% | 0.6000 |
| **最悪3日だけ回避できた（後知恵の上限）** | **+4.323%** | -1.265% | 0.2417 |
| **最良3日を避けてしまった（外した場合）** | **-8.555%** | -9.295% | 1.7753 |
| 最良3日・最悪3日の両方を避けた | -0.302% | -1.877% | 0.3585 |

読み方:
- **DD比 0.60 は「常時 0.62 以下」で機械的に達成できる。** つまり 12週判定（`DEMO_LOOP_V1_OPS.md:181`）の DD 条件は、裁量ではなく単なる縮小でも通る。**だから「LLM を入れたら DD比が下がった」を成果にしない**（§7 の判定を A との比較にする理由）。
- 当てる価値は最大 +8.6pp（最悪3日回避）、外す痛手は -4.2pp（最良3日を避けた場合の差）。**当てられないなら縮小は上昇日の取り分を削るだけ**で、これは 0.75 固定の行が示すとおり（累積 -4.31% → -3.22% だが上昇6日の取り分も 25% 減る）。

### 3-2. 材料を「そのまま」渡さない工夫

- 見出しは**見出し文だけ**（本文は渡さない）。理由: 本文は長く、トークンが 10 倍になり、しかも判断に効くのは見出しの方向性がほとんど。
- 数値は**すべて機械が計算済みの値**を渡し、LLM に再計算させない（`research_brief` の「Arithmetic discipline」と同じ方針。`services/ai_agent.py` の system prompt に既にこの規約がある）。
- 各材料に**証拠 ID**（`news.*` `deriv.funding` `deriv.lsr` `deriv.basis` `sent.fng` `cal.high_impact` `rates.10y` `tech.sma200_distance` `tech.dd365` `book.drawdown`）を振り、LLM はこの ID しか引用できない。
- **鮮度は設計上足りている。** 決定は 00:20 UTC。暗号資産の日足は 00:00 UTC に確定するので、決定が使う終値は 20 分前のもの（`inputs_last_bar_ts`=10-24 は「10-25 00:00 UTC に閉じた足」）。funding と建玉比も 00:00 UTC の 8h/日次区切りで、F&G は日次更新。つまり 8 系統のうち 00:20 時点で古いものはない。
- **未来を見せない。** 渡すのは「決定日より前」の値だけで、約定に使う 01:00 UTC の足は渡さない（既存の commit-before-fill と同じ境界）。実現損益の軌跡も現在の equity/DD 1 点だけにする（過去の当たり外れを渡すと後知恵の学習素材になる）。

## 4. LLM 出力の構造化仕様（受入 (2)）

### 4-1. 出力（1 判断 = 1 オブジェクト）

```json
{
  "action": "hold | reduce | flatten | reenter | abstain",
  "target_weight_total": 0.0,
  "confidence": 0.0,
  "cited": ["tech.dd365", "deriv.lsr", "news.*"],
  "rationale": "280文字以内",
  "invalidators": ["この判断が無効になる条件（3つまで）"]
}
```

- `action` の意味: `hold`=機械のまま / `reduce`=機械の値より下げる / `flatten`=0 / `reenter`=いったん下げた状態から機械の上限まで戻す（＝「買い」はここだけ、上限は機械の値）/ `abstain`=判断しない（機械に委ねる）。
- **`target_weight_total` に「買い増し」の意味は持たせない。** 上限は常に機械側の値（`min(llm, mechanical)`）。レバレッジも、機械が決めた以上のエクスポージャも構造的に作れない。
- 金額・株数・注文は出力させない（発注経路を持たない設計を壊さないため）。

### 4-2. 実測: この形式は実際に成立するか（4構成 × 3回 = 12回）

実データで組んだパケット（4,519 文字 / **2,010 トークン**）を、購読枠の OpenAI 互換 API に投げた実測（`measure2.py` / `measure3.py`）。

| 構成 | 契約検証を通った回数 | 遅延（秒） | 出力トークン | 備考 |
|---|---|---|---|---|
| **reasoning 無効**（`reasoning_effort=none`） | **3/3** | 2.60 / 2.78 / 3.10 | 159 / 172 / 177 | 安定。JSON のみを返す |
| reasoning 有効・上限 700 | 1/3 | 5.46 / 5.86 / 6.39 | 469 / 700 / 700 | **2回は HTTP 200 で本文が空**（推論で 700 を使い切る） |
| reasoning 有効・上限 1600 | 1/3 | 10.47 / 10.86 / 13.34 | 1104 / 1600 / 1600 | 同上（1600 でも空） |
| reasoning 有効・`low` | 0/3 | 6.36 / 6.60 / 6.67 | 800 / 800 / 800 | 同上 |

**これが設計上いちばん重要な実測。** 「HTTP 200 で本文が空」は**エラーにならない失敗**で、素直に実装すると空文字を判断として読むか、例外でループが落ちる。対策は 3 点で、いずれも設計に固定する:
1. **判断呼び出しは推論を切る**（または上限を推論込みで 1,600 以上に取り、`finish_reason=length` を失敗として扱う）。実測の通過率 3/3 対 2/9 が根拠。
2. **必ず契約検証を通す**（下記）。空文字・途中で切れた JSON は「棄却」。
3. **棄却時は機械の値にフォールバック**（リトライは最大 3 回、それでも駄目なら機械）。約定は止めない。

出力例（実測・reasoning 無効の 1 回目、原文ママ）:

```json
{"action":"reduce","target_weight_total":0.6,"confidence":0.62,
 "cited":["tech.sma200_distance","tech.dd365","deriv.lsr","deriv.funding","news.*","sent.fng","book.drawdown"],
 "rationale":"Trend still positive (both >SMA200) but deep 365d drawdowns, crowded longs ..."}
```

### 4-3. 契約検証（機械側。プロトタイプとして実装・実行済み）

検証は「直す」のではなく「棄却する」。判定順は固定（first-hit）。

| 検査 | 規則 | 落ちた場合 |
|---|---|---|
| 1. パース | `json.loads` で dict | 棄却 `not_json` |
| 2. 必須キー | `action` / `target_weight_total` / `confidence` / `cited` / `rationale` | 棄却 |
| 3. `action` | 5 値の enum | 棄却 |
| 4. 重み | `0.0 <= w <= 1.0` の数値（bool 不可） | 棄却 |
| 5. 確信度 | `0.0 <= c <= 1.0` | 棄却 |
| 6. 引用 | `cited` は文字列の配列で、**既定の材料 ID の接頭辞のみ** | 未知 ID は棄却 |
| 7. 上限 | `w > mechanical` は棄却（clamp しない） | 棄却 |
| 8. `abstain` | 他の検査が全部通っていれば「判断なし」＝機械の値 | — |
| 9. 採用 | `effective = min(w, mechanical)`。銘柄へは機械の比率で按分 | — |

- `finish_reason` が `length` / 本文が空 / HTTP 429 → **棄却ではなく「未回答」**（§4-2 の経路へ）。
- 実測では 3/3 の回答が enum・範囲内で、clamp は 0 回。1 回だけ `news.*` の代わりに見出し文字列を引用した（接頭辞規則で通したが、**ID の完全一致を要求すると 1/3 が落ちる**ので、接頭辞＝材料系統の一致で判定するのが実務的）。

### 4-4. 既存 `spec` への落とし方（新しい契約体系を作らない）

既存の決定論的契約にそのまま乗せる。追加するのは「判断の来歴」だけで、実行の意味は変えない。

| 既存の仕組み | 今回の使い方 |
|---|---|

- **コストは無視できる**（年間 100 円未満）。判断を毎日 2 回（BTC/ETH）にしても年 24〜101 円。だから「コストが理由で LLM を入れない」は成立しない。判断材料の取得も全部無料（§3-1）。
- 一方で**枠の制約は現実に当たる**。実測中、購読枠（zai）は 14:19 JST に `HTTP 429 / code 1308 "Usage limit reached for 5 hour ... reset at 2026-10-25 15:08:53"` を返した。**毎日 00:20 UTC（09:20 JST）に固定で叩く設計は、5 時間窓の残量次第で 429 を食う。** だから §5 の「429＝未回答＝機械の値」が必須で、しかも `ai_agent._post_json` に既にある 429 バックオフ（`RATE_LIMIT_BACKOFF_SECONDS`）を再利用する。

### 6-2. 遅延が執行に与える影響（数値）

- 決定 `recorded_at` = 10-25 `00:20:32 UTC`。約定価格は `01:00 UTC` の 1h 足始値で、**決定時刻に依存しない**（commit-before-fill の既存契約）。
- 締切を `00:50 UTC` とすると、使える時間は **29.5 分**。
- 実測遅延 2.6〜3.1 秒（推奨構成）＝予算の **0.15〜0.18%**。最悪の 13.3 秒でも 0.75%。リトライ 3 回でも 40 秒＝2.3%。材料取得 0.8 秒。
- **したがって「LLM の遅延が約定価格を悪くする」経路は存在しない。** 遅延の影響は「間に合わなかった日の裁量が消える」だけで、その日の損失は機械と同じ（＝現状と同じ）。
- 締切超過の実害は日次で測れる: ここの日次リターンは平均 -0.249pp、平均絶対値 1.07pp、最大 3.27pp（10-23）。つまり 1 日落とすと最大 3.27pp の裁量が消える。**締切の遵守率を decision 行に記録して監視する。**
